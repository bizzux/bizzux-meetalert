# Getting this running on your machine

I couldn't run commands directly on your computer from this session (no
shell access to it), so these are the exact commands to run yourself,
in order, from a terminal (PowerShell or Command Prompt) on
`thilak-legionpro5`.

## 1. Turn the bundle into a real git repo at the path you asked for

A `MeetAlert.bundle` file (the full repo, including commit history) is
already sitting in `D:\Projects`. Turn it into a working repo:

```powershell
cd D:\Projects
git clone MeetAlert.bundle MeetAlert
cd MeetAlert
```

This creates `D:\Projects\MeetAlert` as a real git repository on branch
`master`, with the one initial commit already in its history. You can
delete `D:\Projects\MeetAlert.bundle` afterwards - it was only there to get
the repo across.

(If `git` isn't recognized, install Git for Windows first:
https://git-scm.com/download/win)

## 2. Install dependencies

```powershell
npm install
```

This was verified to install cleanly and type-check with zero errors
(`npx tsc --noEmit`) before being handed to you.

## 3. Set up Microsoft Graph (Teams/Outlook calendar)

1. Go to https://portal.azure.com → **App registrations** → **New registration**.
2. Name it (e.g. "MeetAlert"), leave supported account types as your
   organization's default, add a redirect URI matching the app's bundle ID
   (`com.indiabees.meetingreminder`, set in `app.json`).
3. Under **API permissions**, add Microsoft Graph → Delegated →
   `Calendars.Read`, and grant admin consent if your tenant requires it.
4. Copy the **Application (client) ID** and paste it into
   `src/services/graphAuth.ts` in place of `TODO-your-azure-app-client-id`.

## 4. Run it

```powershell
npx expo prebuild
npx expo run:android
```

`expo prebuild` generates the native `android/` (and `ios/`) folders - this
project uses native modules (Notifee, MSAL, calendar access) that need a
dev build, not Expo Go.

For iOS you'll need a Mac with Xcode, or `eas build --platform ios` via an
Expo account (see https://docs.expo.dev/build/setup/) - see the spec doc's
"Platform constraints" section for why the iOS alarm behavior differs from
Android's.

### Google Sign-In and the debug keystore

`android/` is gitignored and fully regenerated by `expo prebuild` - including
`android/app/debug.keystore`, which gets a brand new random signing key if it
isn't already on disk when prebuild runs (a `--clean` prebuild, or just
deleting `android/`, triggers this). That silently breaks Google Sign-In: the
app's SHA-1 fingerprint stops matching the Android OAuth client registered
for it in Google Cloud (the "bizzux-meet" project - see
`src/services/googleSignIn.ts`), and sign-in fails with `DEVELOPER_ERROR`.

This happened once already. The fix: `keystores/debug.keystore` (committed to
git, outside `android/`) is now the one and only debug keystore this project
ever uses - `plugins/withStableDebugKeystore.js` copies it into
`android/app/debug.keystore` on every prebuild, clean or not, so the signing
key (and its SHA-1) never changes again. You shouldn't need to do anything
for this to keep working.

If `DEVELOPER_ERROR` ever comes back anyway, it means the SHA-1 Google has on
file doesn't match `keystores/debug.keystore` anymore (e.g. someone
registered a different fingerprint there, or the file itself got replaced).
Get the current fingerprint with:

```powershell
keytool -list -v -keystore keystores\debug.keystore -alias androiddebugkey -storepass android -keypass android
```

and make sure that exact SHA-1 is registered on the Android OAuth client for
`com.bizzux.bizzminder` in the **bizzux-meet** Google Cloud project (APIs &
Services → Credentials) - not the `bizzux-meetly` Firebase project, which
only holds the web client used alongside it.

## 5. Trial gate + Razorpay payment setup

This wires up: a trial that starts automatically for every new sign-up (30
days by default - see 5i for how an admin can change that, or turn trials
off altogether), a lock screen once it lapses, and a Razorpay checkout that
unlocks the app for a year on payment. Three things need setting up before
any of it works end to end - do them in this order.

### 5a. Install the two new packages

```powershell
npm install
npx expo prebuild --clean
```

`@react-native-firebase/functions` and `react-native-razorpay` are both
native modules - a Metro-only reload won't pick them up, you need the
prebuild + a fresh `npx expo run:android --variant debug` (same as every
other native dependency change this project has needed so far).

### 5b. Upgrade bizzux-meetly to the Blaze plan

Cloud Functions (the code in `functions/`) don't run at all on the free
Spark plan. In the Firebase Console: bottom-left **Upgrade** link → choose
**Blaze (Pay as you go)** → attach a billing account. The free monthly
quota (2M function invocations, etc.) still applies on Blaze - at this
app's current scale you're very unlikely to be charged anything, but a
billing account has to be on file for Cloud Functions to deploy at all.

### 5c. Create a Razorpay account and store its keys as Cloud Functions secrets

1. Sign up at https://razorpay.com (or sign in if you already have an
   account) and complete KYC - Razorpay won't release Live mode keys
   until that's done, so start this early if you haven't already.
2. In the Razorpay Dashboard: **Settings → API Keys → Generate Live Key**.
   Copy the **Key Id** and **Key Secret** immediately - the secret is only
   shown once.
3. From this project's root, store them as Cloud Functions secrets (never
   paste these into any file in the repo):
   ```powershell
   npm install -g firebase-tools   # skip if you already have it (you installed this for BizzMinderAdmin)
   firebase login
   firebase functions:secrets:set RAZORPAY_KEY_ID
   firebase functions:secrets:set RAZORPAY_KEY_SECRET
   ```
   Each command prompts you to paste the value, then stores it encrypted -
   `functions/index.js` reads both at runtime via `defineSecret()`, and
   they're never written to disk in this repo.
4. Deploy the functions:
   ```powershell
   firebase deploy --only functions
   ```
   This also needs the Blaze upgrade (5b) done first, or it fails with a
   billing-related error.

### 5d. Plan pricing - admin-editable, no redeploy needed (see 5j)

There are two plans (annual and monthly). Each plan's actual price and its
crossed-out "regular" price are admin-editable from BizzMinder Admin's
Settings tab, starting the moment they're saved - see 5j below for the
full mechanism. `functions/index.js`'s `DEFAULT_PLAN_PRICES` and
`src/services/razorpay.ts`'s `DEFAULT_PLAN_DISPLAY` are both just
fallbacks for before an admin has ever saved anything there, and MUST be
kept in sync with each other by hand if you ever change them (there's no
shared config file between the mobile app and `functions/` - two separate
deploy targets). Plan DURATION (30 or 365 days) is different - that's
fixed in code, not admin-editable at all; see 5j for why. Today's actual
prices (i.e. these fallbacks, until an admin changes something):

| Plan | Launch price | Standard price shown struck through | Save badge |
|---|---|---|---|
| Annual | ₹1,999/year (≈₹167/mo) | ₹2,988/year (12 × monthly's launch price) | Save 33% |
| Monthly | ₹249/month | ₹399/month | none |

There is deliberately only ONE savings percentage on the whole paywall.
Both cards show a plain struck-through price now (so the "launch pricing"
framing reads consistently), but only annual's is paired with a numeric
"Save %" badge - monthly's ₹399 is the standard price this launch rate
reverts to, shown as a quiet crossed-out number with no percentage
attached. An earlier version gave each plan its own independent "% off
its own regular price" (e.g. monthly showing 38% off while annual showed
33% off), and having two differently-anchored percentages on screen at
once was exactly what read as confusing: there was no single answer to
"what does the discount even mean here." If you revisit either plan's
price, keep this single comparison intact rather than reintroducing a
second percentage.

One more thing worth knowing: both plans are one-time purchases for a
fixed term (30 or 365 days), not an auto-renewing subscription - nothing
charges the user again automatically when a plan runs out, they just see
the paywall again and buy another term. That's deliberately the simpler
build (Razorpay's recurring/UPI-autopay "Subscriptions" API, webhook
handling for renewal failures, and a dunning flow are a meaningfully bigger
project than this). Worth adding a "your plan expires in N days" in-app
reminder before that becomes a support headache, but nothing here depends
on it yet.

### 5e. Before you publish this to the Play Store with Razorpay live

Google Play's payments policy requires Google Play's own billing system to
be offered (at minimum alongside any alternative) for in-app digital
subscriptions on apps distributed via the Play Store - this applies to
India today. Shipping Razorpay as the *only* way to pay, with the app
distributed through the Play Store, risks a policy rejection or takedown.
Two compliant paths, neither started yet:
- Enroll in Google Play's "alternative billing" (user choice billing)
  program in Play Console (Settings → Alternative billing) - this requires
  PCI DSS self-certification, a way for users to report fraudulent
  transactions, and reporting every alternative-billing transaction to
  Google within 24 hours. In exchange, Google's cut drops by 4 percentage
  points on transactions paid through Razorpay.
- Or add Google Play Billing (`react-native-iap` or similar) as the
  primary/only path instead of Razorpay, and accept Google's flat 15%
  service fee on subscriptions (current India rate) with no extra
  compliance work.
This is a decision to make before the Play Store listing goes live, not
before this trial-gate code can be tested - Razorpay works fine for
sideloaded/internal-testing builds in the meantime.

### 5f. The trial countdown banner and early checkout

The Home screen (`TodayScreen.tsx`) now shows a `TrialBanner` right under
its header for as long as a signed-in user is inside their free trial:
"N days left in your trial", a progress bar that fills in day by day
(scaled to that user's own trial length, not a hardcoded number - see 5i),
and a "Make payment" link. It disappears on its own once someone
has ever paid (`TrialStatus.hasPaid`, set from `lastPaymentPlan` on the
user's Firestore doc) or once the trial has actually expired, since
RootNavigator's forced paywall takes over the whole app at that point
instead.

"Make payment" pushes the same `PaywallScreen` onto the main stack early
(a new `Paywall` route registered alongside `Tabs`/`AddMeeting`/`Alarm` in
`navigation/index.tsx`), as a modal, so someone can look at pricing before
they're forced to. `PaywallScreen` itself reads the live trial status
(not which path it was reached by) to decide whether Subscribe is
actually enabled - `locked` is true for as long as `status.expired` is
false, which disables the Subscribe button (via `GradientButton`'s own
`disabled` prop) and shows "Unlocks once your trial ends in N days"
underneath it. A close button appears in this mode too
(`navigation.canGoBack()` is how the screen tells "reached early" apart
from "forced" - there's no route param for it), so there's a way back to
the app without signing out.

`src/store/trialStore.ts` exports `daysUntil(date)`, a small shared helper
so the banner and the paywall screen can never disagree on the day count
for the same `trialEndsAt`.

One thing this does NOT do yet: nothing re-reminds a user once they HAVE
paid that their current paid term is running low - that's the separate
"your plan expires in N days" reminder mentioned in 5d above, still not
built.

### 5g. Accounts that signed up before any of this existed

`onUserProfileCreated` only fires on Firestore's onCreate event - it
stamps trialEndsAt the moment a brand new users/{uid} doc is created, but
it can't reach back and stamp one that already existed before this trial
system did. Every account signed up before today has no trialEndsAt at
all, which both the paywall gate and TrialBanner read as "not expired yet"
(the safe default - see cloudProfile.ts), so those accounts just never see
either one, with no error and no warning.

`functions/scripts/backfillTrial.js` is the one-time fix - a local Admin
SDK script (not deployed, not called by the app) that finds every
users/{uid} doc missing trialEndsAt and gives it a fresh 30-day trial
starting from whenever you run it. It needs a service account key from
Firebase Console (Project settings → Service accounts → Generate new
private key, saved as `functions/scripts/serviceAccountKey.json` -
already gitignored, never commit it), then from `functions/`:

```powershell
node scripts/backfillTrial.js
```

It only ever touches a doc with no trialEndsAt at all, so it's safe to run
more than once and can never reset a trial that's already running, already
expired, or already converted into a paid term. This doesn't need the
Blaze upgrade or Razorpay keys (5b/5c) - it talks to Firestore directly,
so it works even before the rest of section 5 is set up.

### 5h. Error messages shown to users

Every alert the app shows (`showAlert()`, `src/services/appAlert.ts`) was
audited to make sure none of them ever surface a raw SDK/technical string -
things like Firebase's `auth/invalid-credential`, MSAL's `userCancel`, or a
Cloud Function's internal error text. Two real leaks were found and fixed:

- **Microsoft connect** (`src/screens/SettingsScreen.tsx` /
  `src/services/graphAuth.ts`): simply backing out of the Microsoft login
  screen was showing a "Couldn't connect Microsoft account" / "userCancel"
  dialog. `graphAuth.ts` now exports `isUserCancelled()` (recognizes a
  cancel from MSAL's error code/message) and `friendlyConnectError()` (a
  plain message for a real failure) - Settings uses these instead of
  `err?.message`, and shows nothing at all when it was just a cancel,
  matching how Google Sign-In already behaves.
- **Firebase Auth** (`src/store/authStore.ts`) and **Razorpay checkout**
  (`src/services/razorpay.ts`): both had a fallback path that showed
  `err?.message` when the error wasn't one of the specifically-handled
  cases - now a generic "Something went wrong" / "Could not start
  checkout" message instead, never the raw error.

Every other `showAlert(...)` call in the app was already hand-written,
friendly copy (confirmations, permission prompts, sync-failure summaries
that swallow the real error and show a canned message) - nothing else
needed changing. Worth re-checking this if a new SDK integration or Cloud
Function call is added later: the rule is never pass `err.message` (or
`err.code`) straight into `showAlert()`.

### 5i. Admin control over the trial length, and turning trials off

There's a single Firestore doc, `config/trial` (`{ enabled: boolean,
lengthDays: number }`), that controls what a brand-new sign-up gets from
now on. It's not touched by this app at all - `onUserProfileCreated`
(`functions/index.js`) reads it via `readTrialConfig()` the moment a new
`users/{uid}` doc is created, and that's the only place it's ever read on
this side. Nothing here writes to it; it's edited from the companion admin
web app (BizzMinderAdmin's repo), Settings tab, which both reads and
writes it live.

If the doc doesn't exist yet (a brand-new deploy, before any admin has
opened that Settings tab), `readTrialConfig()` falls back to today's
original behavior - trials enabled, 30 days - so nothing changes until an
admin actually sets something.

Turning trials off (`enabled: false`) does NOT lock new sign-ups out
immediately - the opposite: `onUserProfileCreated` simply never stamps a
`trialEndsAt` on their doc at all, and a missing `trialEndsAt` is exactly
what both the paywall gate and `TrialBanner` already read as "not expired"
(see 5g above, and `cloudProfile.ts`'s `toTrialStatus()`) - unlimited free
access, no countdown, no paywall, until an admin turns it back on. This was
a deliberate product decision, not a default anyone should assume:
disabling trials is a soft, reversible "let everyone in free for now," not
a hard paywall.

Either way, this setting is forward-only: it only ever affects accounts
created from the moment it's saved onward. Nobody already signed up - mid
trial, already expired, or already converted to paid - is touched by it.
Changing a trial that's already running for one specific person is still
done the same way as before this existed: hand-edit that person's
`trialEndsAt` from BizzMinderAdmin's Users tab.

`TrialBanner`'s progress bar no longer assumes a fixed 30-day span - it
computes the user's actual trial length from `trialEndsAt - createdAt`
(both now read off the user's Firestore doc via `cloudProfile.ts`'s
`TrialStatus.createdAt`), falling back to 30 days only for the rare older
doc that's missing a `createdAt`. This matters now that `lengthDays` is
admin-configurable and different users can have different trial lengths.

### 5j. Admin control over subscription pricing

Each plan's price, and the crossed-out "regular" price shown next to it on
the paywall, lives in a second Firestore doc, `config/pricing`
(`{ annual: { priceInr, regularPriceInr }, monthly: { priceInr,
regularPriceInr } }`), edited from the same BizzMinder Admin Settings tab
as the trial setting (5i), in its own "Subscription pricing" card. Unlike
`config/trial`, this one doc is read from THREE places, not one:

- `functions/index.js`'s `createRazorpayOrder` reads it (via
  `readPricingConfig()`) the moment someone taps Subscribe, to decide what
  the actual Razorpay order is created for - this is still the only place
  that decides what anyone is really charged, same as before this existed.
- The mobile app's `PaywallScreen` reads it too, live, through
  `store/pricingStore.ts`'s own Firestore listener - not just at checkout -
  so the price shown on the paywall itself updates the moment an admin
  saves a change, with no app restart and no need to start a checkout
  first. This is why `firestore.rules`' `config/{id}` rule had to change:
  `config/pricing` is readable by any signed-in user, while every other doc
  under `config/` (just `config/trial` today) stays admin-read-only - see
  that file's own comment.
- BizzMinder Admin's Settings tab reads and writes it, same as any other
  setting here.

Unlike the trial setting, this one is NOT forward-only: a price change
applies to every user immediately, the moment it's saved - there's no
"existing users keep the old price" scope, because unlike a trial there's
no per-user concept of a price someone already locked in. The one actual
exception is in-flight, not per-user: a Razorpay order already created
(i.e. someone already looking at the native checkout sheet) keeps whatever
price it was created with - `createRazorpayOrder` doesn't re-run once the
sheet is open, so a price change mid-checkout never changes what that one
order charges, it just takes effect for the next person (or the same
person's next attempt).

Plan LENGTH (30 days monthly, 365 days annual) is deliberately NOT part of
`config/pricing` and isn't admin-editable at all - `functions/index.js`'s
`PLAN_DURATIONS` is its only source of truth, unchanged by anything in
Settings. This was a deliberate scope decision, not an oversight: pricing
alone covers "what does BizzMinder cost," without also re-litigating how
long a term already purchased runs for.

The "Save %" badge on the annual card is never stored anywhere as its own
number - both `functions/index.js`'s `readPricingConfig()` comment and
`store/pricingStore.ts` compute it live from whatever `priceInr` /
`regularPriceInr` are actually in effect, so an admin changing either price
can never leave a stale percentage on screen. The monthly card still never
shows that badge at all, by the same design decision documented in 5d.

### 5k. Producing a Play Store release build

EAS Build is already set up for this project - `eas.json` has a
`production` profile with `"buildType": "app-bundle"` (the `.aab` format
Play Store requires, not a raw `.apk`), and `app.json` already carries an
EAS `projectId` (`70d792dd-d31d-4d49-9801-a7582dcf1087`) under the
`bizzux` owner. There is no release keystore anywhere in this repo yet -
only `keystores/debug.keystore`, used for local dev - which is fine: EAS
generates and stores a release keystore in the cloud the first time you
build, so you never have to create or back one up yourself.

Steps, from `D:\Projects\MeetAlert` in PowerShell:

1. One-time: `npm install -g eas-cli`, then `eas login` with whichever
   Expo account owns the `bizzux` org this project's `projectId` belongs
   to.
2. `app.json`'s `android` block has no `versionCode` yet, and
   `eas.json`'s `"appVersionSource": "local"` means Android's versionCode
   is tracked there, not auto-generated. Add `"versionCode": 1` under
   `android` before the first build, and bump it by 1 before every build
   you intend to upload afterwards - Play Console rejects a re-upload
   that reuses a versionCode already seen for this app.
3. `eas build --platform android --profile production`. First run asks
   whether to generate a new Android keystore - say yes. This builds in
   Expo's cloud (runs the native `prebuild` step itself, including every
   plugin under `plugins/` and all native modules such as
   `@react-native-firebase/*` and `react-native-razorpay`) and produces a
   downloadable `.aab`.
4. First time only: create a Google Play Developer account
   (https://play.google.com/console, $25 one-time), create the app
   listing, and fill in the store listing, content rating, and data
   safety form Play Console requires before it accepts any upload.
5. Upload the `.aab` to Play Console's Internal testing track first -
   either manually from the EAS build page, or with
   `eas submit --platform android` (needs a Google Cloud service-account
   key with Play Console API access, which `eas submit` prompts for on
   first use).

Before moving this past internal testing to a public track, resolve 5e
first - Razorpay as the only payment method is fine for
internal-testing/sideloaded builds, but risks a policy rejection or
takedown once the listing goes public.

This covers Android only. Nothing iOS-specific exists in this project yet
- no `GoogleService-Info.plist`, no iOS build profile in `eas.json`, and
no native `ios/` folder has ever been generated - so an App Store (Apple)
release would need that setup done first, separately from the steps
above.

### 5l. Testing a release build on your own phone (no Play Store)

`eas build --platform android --profile production` (5k) produces a
`.aab`, and that format is Play Store-only - you can't install it
directly on a phone. For testing a release-configured build on your own
device, use the `preview` profile instead, already defined in
`eas.json` (`"distribution": "internal"`, `"buildType": "apk"`) - it's a
real release build, not the dev client you use for local development,
just packaged as a directly installable `.apk` instead of a Play Store
upload.

Steps, from `D:\Projects\MeetAlert`:

1. One-time, if not already done: `npm install -g eas-cli`, `eas login`.
2. `eas build --platform android --profile preview`
3. When the build finishes, EAS prints a build page URL with a QR code
   and a direct download link. Open that link in your phone's browser
   (or scan the QR code with the phone's camera) to download the `.apk`
   straight to the phone.
4. Install it. Android will likely ask to allow installing from this
   source the first time - approve that, then it installs like any
   other app.

A release-signed build (whether `preview` or `production`) uses a
different signing key than the debug builds covered in section "Google
Sign-In and the debug keystore" above, so if Google Sign-In matters for
this test, that release keystore's SHA-1 fingerprint needs registering
too, in the same Firebase/Google Cloud Console place the debug one is
registered - otherwise Google Sign-In fails on this build specifically
even though it works fine in dev.

This stays entirely outside Play Store review, so it's unaffected by
the Razorpay payment-policy question in 5e - that only matters once a
listing goes public.
